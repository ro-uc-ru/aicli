# 004-add-command: `aicli add` command (feature selector and shared mechanism)

- Status: approved
- Owner:  ro-uc-ru
- Date:   2026-10-19

## 1. Context

### Goal (required)
`aicli add` is the entry point for adding optional AI/LLM capabilities ("features") to an existing aicli project. Each feature is a subcommand of `add`, specified on its own. Run with no arguments in a terminal, `add` shows a selector of the available features in the style of the home screen; choosing one asks, in a form, for the inputs that feature requires, shows a confirmation with the equivalent command and then runs it. Run without a terminal it prints the list of features as plain text. This spec also fixes the shared mechanism by which a feature creates its files in the project, so every feature behaves the same way when files already exist or a write fails.

### Why (required)
Optional capabilities are never part of the base skeleton (STK-5), so they need one convention for entering a project afterwards. Without it, each future feature would invent its own way of being discovered, asking for inputs and writing files. Features are discovered from the command tree at runtime, as the home screen does, so a new feature appears in the selector with no change to this spec. This spec ships no real feature: it is the foundation the feature specs depend on.

### Optional
- Users / Beneficiaries: data scientists and AI engineers adding an optional capability to their project; authors of future feature specs, who get discovery, prompting and safe file creation without writing them.
- Definitions:
  - Feature: a direct subcommand of `add` that is runnable and is not `help`, whether hidden or unavailable or not. Its name is the command name (e.g. `feature-1` in `aicli add feature-1`). Subcommands of a feature are not features. A feature has no aliases (FR-003).
  - Listed feature: a feature that is available (Cobra `IsAvailableCommand`) and is not hidden. Only listed features appear in the selector, the static list, the home screen and the `Did you mean` line; any feature can be run directly (FR-006).
  - Feature input: a named positional argument that the feature declares, each with a name and a one-line description, in a fixed order. A feature takes exactly as many positional arguments as it declares inputs, and its usage line shows them after its name as `<name>` (e.g. `aicli add feature-1 <input-1> <input-2> [flags]`). The flags of a feature are options with defaults, not inputs: the form never asks for them. An input may also declare either a list of choices (a non-empty, ordered list of allowed values) or a validator (FR-014), not both (FR-003).
  - Choice input: a feature input that declares a list of choices (FR-016).
  - Validator: a function that a feature input may declare, which takes the trimmed value and returns either success or a one-line error message; it has no side effects: it does not read or write files, spawn processes or use the network (FR-014).
  - Feature plan: the list of feature files that a feature would create for a given set of input values, which the feature computes without side effects and without writing anything; it is the same list the feature passes to the shared mechanism when it runs with those values. Every feature declares at least one feature file. Computing the plan may fail with a one-line error message (e.g. a combination of values the feature does not support); the confirmation then behaves as for a failed check of FR-022 (FR-018), and a run of the feature fails as in ERR-5 and FR-026 with `Error: <message>`, creating nothing.
  - Equivalent command: `aicli add <feature>` followed by the values of the inputs in declaration order, each shown as is when it is non-empty and contains only ASCII letters, digits and the characters `_ @ % + = : , . / -`, and otherwise wrapped in single quotes with each `'` inside it written as `'\''` (e.g. `'hola mundo'`, `'it'\''s'`), with `--` inserted before the first value when any value starts with `-`.
  - Feature file: a file that a feature creates in the project through the shared mechanism of FR-022..FR-025, given as a path relative to the project root, the embedded template it is rendered from and the data the feature passes to that template (at least the input values).
  - Selector: the interactive screen of FR-008.
  - Form: the interactive prompt of FR-011.
  - Confirmation: the interactive step of FR-018.
  - Interactive mode, static mode, styled: as defined in spec 003 (interactive mode: stdin and stdout are TTYs and `TERM` is not `dumb`; styled: `NO_COLOR` unset or empty and `TERM` not `dumb`).
  - Project root: as defined in spec 002.
- Fixed texts (English, like the rest of the CLI):
  - Selector header: `aicli › add`
  - Selector description line: `Add an AI/LLM feature to this project.`
  - Empty list line: `No features available.`
  - Form and confirmation header: `aicli › add › <feature>`
  - Confirmation buttons: `Add` and `Cancel`
  - Line printed after `Cancel`: `Nothing added.`
  - Form error for an empty value: `<input> cannot be empty`
  - Error for a value outside the choices: `<input> must be one of: <choice-1>, <choice-2>`
  - Error for a value with control characters: `<input> contains control characters`
  - Confirmation file list heading: `Will create:`
  - Confirmation heading when files already exist: `Cannot add <feature>, these files already exist:`
  - Static list closing line: ``Run `aicli add <feature> --help` to see its inputs.``
  - Success line: `Added <feature>` (styled: `✓ Added <feature>`)
  - Next steps heading: `Next steps:`
- Notes for the plan (non-normative):
  - The list of features is read from the Cobra tree each time `add` runs; no feature is named in this feature's code. Each future feature is one flat folder under `cmd/` (e.g. `cmd/addfeature1`) that registers itself as a subcommand of `add`, declares its inputs through a helper in `internal/` (e.g. stored in Cobra `Annotations`) and keeps its templates under `templates/`.
  - `add` is not declared exempt from the check of spec 002, so it and every feature are checked by default, and the home screen of spec 003 lists them like any other command.
  - The selector reuses the list behaviour of the home screen (pointer, keys, mouse, scrolling, resize, truncation); the sharing lives in `internal/tui` (ARC-7). The form and the confirmation are built with Bubble Tea, Lipgloss and `bubbles` (`textinput`), already direct dependencies, inside the same Bubble Tea program as the selector; Huh is not used and no new dependency is added (STK-2, STK-4).
  - A feature declares, through the same helper in `internal/`, its inputs (with optional choices or validator), the function that computes its feature plan from the input values, and its optional next-steps lines (FR-025).
  - The feature runs in-process through the Cobra command, never by spawning `aicli` again (SEC-6), with the input values passed as its positional arguments.
  - The shared file mechanism lives in `internal/` and takes the project root from the check of spec 002 (its FR-009). Exclusive creation (no-replace) may use `golang.org/x/sys` (STK-6).
  - The end-to-end flow is verified with a feature registered only in tests, which declares inputs and files; it is not part of the real tree.
  - Non-normative mockups: `designs/add-screen.md`.
  - The golden file of the home screen's static output with the real command tree changes when `add` is registered; regenerating it with `-update` is part of this spec and, as spec 003 states, does not count as a change to spec 003.

## 2. Functional Requirements

- FR-001 (ubiquitous)    The CLI shall provide the command `aicli add` as a grouping command whose features are its subcommands. `add` and every feature shall be subject to the project root check of spec 002 (not exempt). The check shall run before any other logic of `add`, including FR-007, so that outside a project root `aicli add`, `aicli add <feature>` and `aicli add <unknown>` fail as in spec 002 FR-003 without showing the selector, the form or the confirmation and without creating any file; `--help` and `help add` keep working in any directory (spec 002 FR-007).
- FR-002 (ubiquitous)    The list of listed features shall be built from the command tree each time `aicli add` runs, so that a listed feature registered under `add` appears in the selector and in the static list with no other change; no feature shall be named in the code of this spec.
- FR-003 (ubiquitous)    Every feature registered under `add` shall follow the feature contract: it declares no aliases; its input names are non-empty and unique; each choice input declares a non-empty list of distinct, non-empty choices; no input declares both choices and a validator; and it declares the function that computes its feature plan. A test over the command tree shall fail, naming the feature and the rule it breaks, when any feature does not follow it.
- FR-004 (ubiquitous)    The home screen of spec 003 shall list `add` and each listed feature (as `add <feature>`) by its own rules (spec 003 FR-003, FR-004, FR-012), with no change to spec 003; a hidden or unavailable feature is not listed there either.
- FR-005 (state-driven)  WHILE in static mode, WHEN `aicli add` is run with no arguments and no flags inside a project root and `add` has at least one listed feature (otherwise EC-003), the CLI shall print to stdout once, as plain text with no ANSI, mouse or terminal control sequences: the header, the description line, a blank line, one line per listed feature (name padded to a common width, then the short description), a blank line and the closing line ``Run `aicli add <feature> --help` to see its inputs.``, ignoring the terminal width, and exit with code 0 without asking for anything.
- FR-006 (event-driven)  WHEN `aicli add <feature>` is run with a feature name inside a project root, the CLI shall show neither the selector, the form nor the confirmation, and shall run the feature with the given flags and the positional arguments trimmed of leading and trailing whitespace, as the form does (FR-013). The arguments shall be checked in this order, and the first failure shall make it fail as in ERR-5 and FR-026, run nothing and create no file; the second line of each message is the usage line of the feature:
  1. too few arguments, where `<input>` is the first missing input:
     ```
     Error: <feature> requires <input>
       Usage: aicli add <feature> <input-1> <input-2> [flags]
     ```
  2. too many arguments:
     ```
     Error: <feature> takes <n> argument(s), got <m>
       Usage: aicli add <feature> <input-1> <input-2> [flags]
     ```
  3. then, for each input in declaration order, the first value that is empty after trimming, contains a control character (EC-013), is not one of the choices of a choice input (FR-016), or fails its validator (FR-014), with the first line `Error: <input> cannot be empty`, `Error: <input> contains control characters`, `Error: <input> must be one of: <choice-1>, <choice-2>` or `Error: <message of the validator>`:
     ```
     Error: <input> cannot be empty
       Usage: aicli add <feature> <input-1> <input-2> [flags]
     ```
- FR-007 (unwanted)      IF, inside a project root, `aicli add` is run with an argument that is not the name of any feature, listed or not (and not a flag), THEN the CLI shall fail as in ERR-5 and FR-026 with exit code 1, create no file and show neither the selector, the form nor the confirmation, with these lines; the `Did you mean` line appears only when one or more listed features are close to `<arg>` by the rule Cobra uses for its own suggestions, naming them in list order:
  ```
  Error: unknown feature "<arg>"
    Did you mean "<feature>"?
    Run `aicli add` to see the available features.
  ```
- FR-008 (state-driven)  WHILE in interactive mode, WHEN `aicli add` is run with no arguments and no flags inside a project root and `add` has at least one listed feature (otherwise EC-003), the CLI shall show the selector in the terminal's alternate screen: the header `aicli › add`, the description line, a blank line, one entry per listed feature in the order Cobra gives them (the feature name padded to a common width, then its short description), a pointer `> ` marking exactly one entry (starting on the first), and a footer listing the valid keys (move, select, quit). The selector shall not show the large `AICLI` banner.
- FR-009 (ubiquitous)    The list of the selector shall behave as the list view of the home screen for the pointer, movement keys, mouse wheel, scroll indicators, highlight colours (when styled), terminal resize and mouse capture (spec 003 FR-005, FR-006, FR-011, FR-013, FR-015, FR-020), with these differences: `Enter` or a click selects the feature instead of opening a detail view; `q`, `Esc` and `Ctrl+C` quit.
- FR-010 (event-driven)  WHEN, in the selector, the user presses `Enter` or clicks on an entry, the CLI shall stay in the alternate screen and show the form of that feature (FR-011), or its confirmation (FR-018) if it has no feature inputs. WHEN the user presses `q`, `Esc` or `Ctrl+C` in the selector, or `Ctrl+C` in the form or the confirmation, the CLI shall restore the terminal (leave the alternate screen, release the mouse), leave nothing printed, create no file, run no feature and exit with code 0. `Ctrl+C` here is the key read by the screen, not a signal (see EC-020).
- FR-011 (state-driven)  WHILE the selected feature has one or more feature inputs, the CLI shall show the form in the alternate screen: the header `aicli › add › <feature>`, the description of the feature (FR-012), a blank line, then one field per input in declaration order (a text field, or a choice field for a choice input, FR-016), all visible at once when the terminal is tall enough (otherwise EC-010), each with the input name as title and the input description below it, and a footer listing the valid keys for the focused field. The blank line above the first field and the line above the footer are the scroll-indicator lines of the fields, as in spec 003 FR-020 (`↑ more`, `↓ more`, otherwise blank). The focused field shall be marked by a `> ` prefix on its title, and every other title by two spaces, so that the focus is visible without colour; when styled, the focused title is also highlighted. Focus starts on the first field.
- FR-012 (ubiquitous)    The form and the confirmation shall show, below their header, the description of the feature: its Cobra short description, as one line; the long description is not shown (it stays available through `aicli add <feature> --help`). When styled the description may be dimmed; styling only adds ANSI sequences. The description is part of the alternate screen and is never printed to the normal screen; a direct call `aicli add <feature>` (FR-006) does not show it.
- FR-013 (unwanted)      The form shall trim leading and trailing whitespace from each value of a text field. IF a trimmed value is empty, THEN the form shall show the error `<input> cannot be empty` under that field and keep the focus on it; ELSE IF the input declares a validator (FR-014) and it returns an error message, THEN the form shall show that message under the field in the same way. The feature shall not run until every input holds a value that passes these checks. Any validation that needs side effects belongs to the feature when it runs.
- FR-014 (event-driven)  WHEN the value of an input that declares a validator is checked (on leaving the field, FR-015; on `Enter` on the last field; or on a direct call, FR-006), the CLI shall call the validator with the trimmed value and, if it returns an error message, show it as FR-013 states (form) or fail with it as FR-006 states (direct call). The validator shall be called only after the value has been found non-empty and free of control characters.
- FR-015 (event-driven)  WHEN, in the form, the user presses `Tab` or `Enter` on a field that is not the last, the focus shall move to the next field after validating the field it leaves (FR-013); `Shift+Tab` shall move it to the previous field without validating. `Enter` on the last field shall validate every field and, if all are valid, show the confirmation (FR-018); otherwise the focus moves to the first invalid field. The form shall capture the mouse, as the list of the selector does: a click on a field (its title, description, input line or, for a choice field, any of its options) shall move the focus to it without validating, like `Shift+Tab`; a click on an option of a choice field also selects that option.
- FR-016 (state-driven)  WHILE a choice field has the focus, it shall show every choice of the input on its own line, in declaration order, with `(•) ` before the selected one and `( ) ` before the others, so that the selection is visible without colour; `↑`/`↓` (and `k`/`j`) shall move the selection to the previous or next choice, staying put at the first or last. The selection starts on the first choice. WHILE it does not have the focus, it shall show only the selected choice. A choice field cannot be empty and needs no other validation.
- FR-017 (event-driven)  WHEN, in the form, the user presses `Esc`, the CLI shall return to the selector with the pointer on the same feature, keeping the values entered so far for that feature; no feature shall run and no file shall be created. WHEN the user opens the form of the same feature again in the same run of `aicli add`, it shall show those values, with the focus on the first field; the form of another feature starts with its own values (empty, or the first choice). The values are kept only in memory and are lost when `aicli add` exits.
- FR-018 (event-driven)  WHEN the user presses `Enter` on the last field of a valid form, or selects a feature that has no feature inputs, the CLI shall show the confirmation in the alternate screen: the header `aicli › add › <feature>`, the description of the feature (FR-012), a blank line, the equivalent command, a blank line, the heading `Will create:` followed by one line per path of the feature plan for the entered values, indented by two spaces and in plan order, a blank line, the buttons `Add` and `Cancel` with the focus starting on `Cancel`, and a footer listing the valid keys. The focused button shall be drawn as `[ <label> ]` and the other as `  <label>  ` (same width), so that the focus is visible without colour; when styled, `Add` and `Cancel` shall be drawn in two different colours, focused or not, and the focused one is also bold. Before showing it, the confirmation shall compute the feature plan and run on it the checks of FR-022 and FR-023 without writing anything. IF computing the plan or any check fails, THEN, in place of `Will create:` and its paths, it shall show the lines of that error without `Error: ` and with the first letter capitalised (for FR-023: `Cannot add <feature>, these files already exist:` and the existing paths), in the error red when styled, and only the `Cancel` button, focused; `y`, `←`, `→` and `Tab` then do nothing. The confirmation shall release the mouse, as the detail view of spec 003 does, so that the user can select and copy the equivalent command with the terminal; its buttons are driven by the keyboard only. `←`/`→` and `Tab` move the focus between the buttons, `Enter` presses the focused one, `y` presses `Add` and `n` presses `Cancel`. `Add` continues as in FR-019; FR-022..FR-024 still run when the feature runs, so that a file that appears after the confirmation is never replaced (EC-018). `Cancel` shall restore the terminal as in FR-010, create no file, run no feature, print the line `Nothing added.` to stdout (plain, no ANSI sequences) and exit with code 0; quitting with `Ctrl+C` prints nothing (FR-010). `Esc` returns to the previous step: the form with the typed values kept, or the selector with the pointer on the same feature if the feature has no inputs.
- FR-019 (event-driven)  WHEN the user confirms with `Add` in the confirmation (FR-018), the CLI shall leave the alternate screen, restore the terminal and then run the feature in the same process as if the user had typed the equivalent command; the output, the exit code and the errors shall be the ones the feature produces.
- FR-020 (ubiquitous)    The selector, the form and the confirmation shall not create, modify or delete any file, shall not spawn any external process and shall not use the network (SEC-4, SEC-6); the only file-system access they make is the read-only check of the feature plan by the confirmation (FR-018); files are created only by the feature, through FR-022..FR-025, after the user confirms with `Add`.
- FR-021 (unwanted)      IF the selector, the form or the confirmation cannot be started, THEN the CLI shall first restore the terminal and then fail as in ERR-5 and FR-026 with the first line `Error: <cause>`; nothing of the selector, the form or the confirmation shall remain on stdout.
- FR-022 (ubiquitous)    The shared mechanism for creating feature files shall take the project root, the feature name and the list of feature files, and shall validate every target path before writing anything: it must be non-empty and relative, use `/` as separator, have no empty, `.` or `..` component (so no leading, trailing or doubled `/`), and, once the project root and the existing parent directories of the target have both had their symbolic links resolved, lie inside the resolved project root. IF any path is invalid, THEN it shall fail as in ERR-5 and FR-026 naming the path, and create nothing (SEC-3). IF the list is empty, THEN it shall fail as in ERR-5 and FR-026 with `Error: <feature> declares no files` and create nothing, since every feature declares at least one feature file.
- FR-023 (unwanted)      IF any target path already exists (of any kind, including a directory or a broken symbolic link), THEN the shared mechanism shall create or modify nothing and fail as in ERR-5 and FR-026 with the following lines, listing every existing path in the order of the list (SEC-5). This is also how a feature that was already added is detected: no other record of added features exists.
  ```
  Error: cannot add <feature>, these files already exist:
    <path>
    <path>
  ```
- FR-024 (event-driven)  WHEN no target path exists and all are valid, the shared mechanism shall first render every feature file in memory from its embedded template and its data (ARC-5); IF rendering any of them fails, THEN it shall create nothing and fail as in ERR-5 and FR-026 naming the path and the cause (ERR-1). WHEN all are rendered, it shall create the missing parent directories and every feature file with its rendered content, creating each file only if it does not exist at the moment of creation, never replacing one (SEC-5). IF creating or writing any file fails, including because it appeared after the check of FR-023, THEN it shall remove every file and directory it created in that run, and nothing else (a directory is removed only if it is empty, never recursively), so that either all feature files exist or none, and fail as in ERR-5 and FR-026 with the error and its context (ERR-1). IF the rollback cannot remove a path it created, THEN the error shall add the continuation line `could not remove:` followed by one line per path left behind, in creation order.
- FR-025 (event-driven)  WHEN all feature files are created, the shared mechanism shall print to stdout one line `create  <path>` per file, in the order of the list, then a blank line and the line `Added <feature>`, and, if the feature declares next steps (zero or more one-line instructions, e.g. an environment variable to set in `.env`), a blank line, `Next steps:` and one line per step indented by two spaces, in declaration order; then it shall return success. WHEN stdout is a TTY and styled, the word `create`, the success line and the next steps shall be styled with Lipgloss as the success output of spec 001 FR-015; styling may only add ANSI sequences and a `✓ ` prefix on the success line, so that stripping both yields exactly the plain lines. Otherwise the lines shall be plain with no ANSI sequences.
- FR-026 (ubiquitous)    Every error introduced by this spec (FR-006, FR-007, FR-021, FR-022, FR-023, FR-024) shall be written as ERR-5 states. WHEN stderr is a TTY and styled, it shall be styled with Lipgloss as in spec 001 FR-023 (red bold `Error:`, dimmed continuation lines); styling may only add ANSI sequences and a `✗ ` prefix on the first line, so that stripping both yields exactly the plain message. Otherwise the message shall be plain with no ANSI sequences.

## 3. Edge Cases

- EC-001 IF `aicli add <arg>` is run outside a project root and `<arg>` is not a feature, THEN the CLI shall fail with the message of spec 002 FR-003, not with the message of FR-007. (FR-001, FR-007)
- EC-002 IF a feature is hidden or unavailable, so it is not a listed feature, THEN it shall not appear in the selector, the static list or the home screen, and it shall still run when called directly as `aicli add <feature>`. A deprecated feature is unavailable and, when run directly, shall print no deprecation notice, so that its output is only the one of FR-025 or its error (ERR-5). (FR-002, FR-004, FR-005, FR-006, FR-007, FR-008, FR-025)
- EC-003 IF `add` has no listed feature, THEN `aicli add`, in interactive mode as well as in static mode, shall not show the selector nor enter the alternate screen: it shall print to stdout, as plain text with no ANSI sequences, the header, the description line, a blank line and `No features available.` (without the closing line of FR-005), and exit with code 0. (FR-005, FR-008)
- EC-004 IF `add` has no listed feature and `aicli add <arg>` is run inside a project root with an `<arg>` that is not the name of any feature, THEN FR-007 applies, without the `Did you mean` line. (FR-007)
- EC-005 IF stdin is a TTY but stdout is not (or the reverse), THEN `aicli add` shall use static mode. (FR-005, FR-008)
- EC-006 IF a feature name or short description contains characters wider than one cell (e.g. CJK, emoji), THEN alignment and truncation shall use the displayed width. (FR-005, FR-008)
- EC-007 IF a feature has no short description, THEN its entry and its static line shall show the name alone. (FR-005, FR-008)
- EC-008 IF the selected feature has no short description, THEN the form and the confirmation shall show no description line and no blank line in its place. (FR-012)
- EC-009 IF a value is not one of the choices of a choice input on a direct call (including a different letter case), THEN FR-006 fails with `Error: <input> must be one of: <choices>`, listing every choice in declaration order separated by `, `. (FR-006, FR-016)
- EC-010 IF, in the selector, the form or the confirmation, the terminal is narrower than an entry, the description line, a header, the feature description of FR-012, a field title, a field description, a choice, a field error or a line of the file list of FR-018, THEN it shall be truncated with `…` and never wrapped; the equivalent command is never truncated and shall be wrapped to the terminal width, so that it is always shown whole. IF the terminal is too short to show everything, THEN the list (in the selector), the fields (in the form) or the paths of the file list (in the confirmation) shall scroll in the remaining space with the header fixed at the top, keeping the entry under the pointer or the focused field, with its error if any, visible; the paths of the file list scroll with `↑`/`↓` and `k`/`j` under the fixed `Will create:` (or `Cannot add …`) heading, with one scroll-indicator line above and one below them (`↑ more`, `↓ more`, otherwise blank), and the footer then also lists `↑/↓ scroll`. IF a focused choice field (FR-016) is taller than the space left for it, THEN its choices shall scroll inside the field, keeping the selected choice visible. IF there is still no room, THEN elements shall be hidden in this order until it fits, as in spec 003 EC-003: first, in the confirmation, the file list with its heading and indicator lines; then the description line or the feature description, then the scroll-indicator lines, then the footer, then the header. IF, in the confirmation, the wrapped equivalent command and the buttons still do not fit, THEN the command shall scroll with `↑`/`↓` and `k`/`j` in the space left above the buttons, starting at its first line. At least one entry, the focused field, or the buttons and one line of the equivalent command shall always remain visible. (FR-008, FR-009, FR-011, FR-012, FR-016, FR-018)
- EC-011 IF the user presses a key that is not listed for the selector, the focused field of the form or the confirmation, THEN nothing shall happen. In a text field the listed keys are printable characters, `Backspace`, `Delete`, `←`/`→`, `Home`/`End` and the keys of FR-010, FR-015 and FR-017; in a choice field, the keys of FR-010, FR-015, FR-016 and FR-017. IF the user clicks outside every entry in the selector, or outside every field in the form, THEN nothing shall happen. (FR-009, FR-010, FR-011, FR-015, FR-016, FR-017, FR-018)
- EC-012 IF the value typed in a text field is wider than the space available to its input line, THEN the input line shall scroll horizontally so that the cursor is always visible; the value shall never be wrapped or truncated, and the full value reaches the feature and the equivalent command. (FR-011, FR-018)
- EC-013 IF the user types or pastes into a text field text that contains control characters (newline, carriage return, tab or any other C0/C1 control or `DEL`), THEN the form shall discard those characters and keep the rest, so that a pasted multi-line text never submits the field; IF a value given to a direct call contains one, THEN FR-006 fails with `Error: <input> contains control characters`. (FR-006, FR-013)
- EC-014 IF the user fills some fields and then presses `Esc` or `Ctrl+C`, THEN no feature shall run and no file shall be created. (FR-010, FR-017)
- EC-015 IF a value typed in the form starts with `-`, THEN it shall reach the feature as a positional argument and not as a flag, and the equivalent command shall show `--` before the first value. (FR-018, FR-019)
- EC-016 IF a value typed in the form contains spaces, quotes or other characters special to a POSIX shell, THEN the feature shall receive it unchanged (after trimming) and the equivalent command shall show it quoted, so that copying the command into a shell passes the same value. (FR-018, FR-019)
- EC-017 IF the user returns from the confirmation to the form with `Esc`, edits a value and continues, THEN the confirmation shall show the equivalent command with the new values. (FR-015, FR-018)
- EC-018 IF a file of the feature plan appears after the confirmation was shown and before the user presses `Add`, THEN the feature shall fail as in FR-023 when it runs and EC-019 applies; nothing is replaced. (FR-018, FR-023)
- EC-019 IF the feature fails after the user confirms with `Add` (e.g. FR-023), THEN the terminal shall be in its normal state, nothing of the selector, the form or the confirmation shall remain, and the CLI shall fail as in ERR-5: stdout empty, the error on stderr, exit code 1. (FR-019)
- EC-020 IF the process receives a signal (e.g. SIGINT or SIGTERM sent with `kill`, or `Ctrl+C` in static mode), THEN the CLI shall restore the terminal if the selector, the form or the confirmation was shown and exit as in ERR-5, with 128 plus the signal number and printing nothing. (FR-005, FR-008, FR-010, FR-011, FR-018)
- EC-021 IF two entries of the list of feature files have the same target path, THEN the shared mechanism shall fail as in FR-022 naming the path and create nothing. (FR-022)
- EC-022 IF a parent of a target path exists and is a regular file, or a target path resolves outside the project root through a symbolic link, THEN the shared mechanism shall fail as in ERR-5 and create nothing. (FR-022, FR-024)
- EC-023 IF the process receives SIGINT or SIGTERM while the shared mechanism is creating feature files, THEN it shall complete the rollback of FR-024 before exiting as in ERR-5 with 128 plus the signal number and printing nothing. (FR-024)

## 4. Scope

### In scope
- The `aicli add` command: selector (interactive), plain list (static), direct call of a feature, unknown-feature error.
- The form that asks for the inputs of the selected feature, the confirmation that shows the equivalent command, and the run of the feature.
- The shared mechanism to create feature files in the project: path validation, no overwriting, all-or-nothing, report.
- Discovery of features from the command tree and the contract a future feature follows (a subcommand of `add` whose declared positional arguments are its inputs, with optional choices or validator, its feature plan and its optional next steps).
- The preview of the feature plan in the confirmation, and the success line and next steps after the files are created.
- The listing of `add` and its features in the home screen of spec 003.

### Out of scope
- Any real feature (e.g. `add feature-1`): each has its own spec, so this one stays small and testable with a test-only feature.
- Editing existing project files or adding Python dependencies (`pyproject.toml`, `Settings`, `.env.example`): it depends on what each feature needs and on STK-4; the first feature spec that needs it decides, and a shared mechanism can come in a later spec.
- Listing, updating or removing installed features: the base skeleton gets no registry file (the layout is fixed, ARC-6), so installed features are only detected through their files (FR-023).
- Prompting when `aicli add <feature>` is called directly with a missing argument: the direct call is for scripts and keeps the non-interactive behaviour of ERR-3.
- Asking for the flags of a feature in the form: flags are options with defaults, set only on the direct call.
- Secret or masked inputs: secrets reach the generated project through environment variables (SEC-1), so no feature input is a secret (ERR-4).
- Search or filtering of the list, themes, configurable colours or texts: fixed by convention.
- Windows support: LIM-1.
- Recovering from an interruption that cannot be caught (SIGKILL, power loss) during file creation: no process can roll back after it; EC-023 covers the signals that can be caught.
