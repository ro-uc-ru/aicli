# 005-add-llm-provider: `aicli add llm-provider` feature

- Status: approved
- Owner:  ro-uc-ru
- Date:   2026-10-21

## 1. Context

### Goal (required)
`aicli add llm-provider` adds one or more LLM providers (`openai`, `claude`, `gemini`, `ollama`) to an existing aicli project: an async client per provider, a shared `llm` service and router with `GET /llm/health` and `POST /llm/{provider}/completion`, their schemas and tests, and the lines each provider needs in existing project files (router registration, dependency, example environment variables). To support it, this spec extends the add mechanism of spec 004 with a multi-choice input that takes several values, the form opened directly by `aicli add <feature>` in a terminal, shared files created only when missing, and lines injected into existing files after a marker.

### Why (required)
Choosing and wiring an LLM provider is the first thing an AI backend needs, and today every project does it ad hoc. SCP-2 puts provider selection in scope and STK-5 requires it to be opt-in, so it arrives as the first real feature of `aicli add`. It is also the first feature that needs to touch files that already exist and to add several items in one run, which spec 004 left to "the first feature spec that needs it".

### Optional
- Users / Beneficiaries: data scientists and AI engineers who want to call one or more LLMs from their FastAPI project with a consistent layout; authors of future features, who reuse the multi-choice input, shared files and injection.
- Definitions:
  - Feature, listed feature, feature input, choice input, validator, feature plan, equivalent command, feature file, selector, form, confirmation, interactive mode, static mode, styled, project root: as in spec 004.
  - Provider: one of `openai`, `claude`, `gemini`, `ollama`, in this order (the declaration order of the choices). The choice name is the one used on the command line and in file names; the environment variables keep the prefix of the vendor's API, which its SDK and documentation use: `OPENAI_` for `openai`, `ANTHROPIC_` for `claude`, `GEMINI_` for `gemini`, `OLLAMA_` for `ollama`.
  - Capability: one kind of operation an LLM client can perform, with its own protocol in `app/ai/llm/base.py` and its own route under `/llm/{provider}/`. This spec defines only the `completion` capability, implemented by every provider; later features add capabilities, possibly to only some providers (e.g. embeddings for `openai` only), by injecting at the markers of FR-022.
  - Multi-choice input: a choice input (spec 004) that takes one or more distinct values from its choices instead of exactly one. Only the last input of a feature may be a multi-choice input. On a direct call it takes all the remaining positional arguments; in the form it is shown as a checklist (FR-006). Its values are always used in the declaration order of the choices, whatever order they were given in (FR-004).
  - Item: what a feature calls each value of its multi-choice input when it reports it (for this feature, a provider; its plural noun is `providers`). A feature may declare, per value, the feature file whose existence means that value is already added (the item file). For this feature the item file of `<provider>` is `app/ai/llm/<provider>.py`.
  - Added provider: a provider whose item file exists in the project, of any kind (FR-023 of spec 004). In the generated app (FR-016..FR-020) it also includes a provider module written by the user with a name outside the choices (e.g. `mistral`), which the registry finds like the others; aicli neither generates nor validates such a module, and what it does is the user's responsibility.
  - File action: what the shared mechanism does with each entry of the feature plan: `create` (a feature file as in spec 004, which must not exist), `shared` (created only if it does not exist, otherwise left untouched), or `inject` (lines inserted into an existing file after a marker line).
  - Marker: a full line of an existing project file whose content, once leading and trailing whitespace is removed, is exactly `# aicli:<name>` (e.g. `# aicli:routers`). Injected lines go right after it, with the same leading whitespace as the marker, so the marker stays and further injections land after it as well.
  - Block: the lines of one `inject` entry, inserted together or not at all (FR-009).
  - Configured provider: an added provider whose required environment variables are set in the generated project to a value that is not empty or whitespace only: `OPENAI_API_KEY` and `OPENAI_MODEL` for `openai`; `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` for `claude`; `GEMINI_API_KEY` and `GEMINI_MODEL` for `gemini`; `OLLAMA_MODEL` for `ollama` (`OLLAMA_BASE_URL` is optional, with default `http://localhost:11434/v1`); for a provider module written by the user, the required variables it declares. No model has a default.
- Fixed texts (English, like the rest of the CLI):
  - Multi-choice form error when nothing is selected: `select at least one <input>`
  - Suffix of an already added choice in the form: `(already added)`
  - Form message when every choice is already added: `All <items> are already added.`
  - Error for a value given twice: `<input> "<value>" is given more than once`
  - Already-added error heading: `cannot add <feature>, these <items> are already added:`
  - Missing marker error: `cannot add <feature>, <path> has no "# aicli:<name>" marker`
  - Repeated marker error: `cannot add <feature>, <path> has more than one "# aicli:<name>" marker`
  - Missing inject target error: `cannot add <feature>, <path> does not exist`
  - Inject target of another kind error: `cannot add <feature>, <path> is not a regular file`
  - Confirmation headings: `Will create:` (spec 004) and `Will update:`
  - Report verbs: `create`, `skip`, `update`, each padded to 6 characters plus two spaces, so paths line up.
- Generated files of the feature (relative to the project root):

```
app/
├── ai/llm/
│   ├── __init__.py          # shared: the provider registry (FR-016)
│   ├── base.py              # shared: capability protocols, message types, provider errors
│   └── <provider>.py        # create, per provider: async client + its settings (item file)
├── services/llm.py          # shared: use cases called by the router (FR-019)
├── api/
│   ├── router.py            # inject at its markers: registers the llm router once
│   └── routers/llm.py       # shared: GET /llm/health, POST /llm/{provider}/completion
└── schemas/llm.py           # shared: request/response models (marker for later capabilities, FR-022)
tests/
├── test_llm_router.py       # shared: router tests with a fake client
└── test_llm_<provider>.py   # create, per provider: settings and registration tests
pyproject.toml               # inject at "# aicli:dependencies": the provider's SDK
.env.example                 # inject at "# aicli:env": the provider's variables, empty values
```

- Generated-project dependencies approved by this spec (STK-4): `openai` (used by `openai` and by `ollama` through its OpenAI-compatible endpoint), `anthropic` (used by `claude`) and `google-genai` (used by `gemini`). Their lower version bounds are fixed in the plan.
- Notes for the plan (non-normative):
  - The extensions to the add mechanism (FR-001..FR-010) live in the same `internal/` packages as spec 004 and are generic: no provider is named there. The feature lives in one flat folder under `cmd/` (e.g. `cmd/addllmprovider`) with its templates under `templates/`.
  - Adding markers to the base skeleton changes files covered by golden files of spec 001 (`app/api/router.py`, `pyproject.toml`, `.env.example`); regenerating them with `-update` is part of this spec and does not change spec 001's tree (its FR-002).
  - So that the blocks injected at the markers of FR-022 need no new import lines, the shared files refer to each other through module imports (e.g. `schemas.<Model>` rather than importing each name), and provider SDKs are imported inside the methods (FR-016).
  - The registry discovers the provider modules present in `app/ai/llm/` (FR-016); it is not filled by injection, since `app/ai/llm/__init__.py` is a `shared` file that does not exist yet on the first run (FR-010) and may be created again in a later one (EC-009).
  - The router imports injected at `# aicli:router-imports` are excluded from import sorting (e.g. ruff's `# isort: off` / `# isort: on` action comments around the marker), since injection after a marker cannot keep a sorted order once several features add routers (FR-015).
  - The golden files of the home screen (spec 003) and of the static `aicli add` list (spec 004, real tree, until now `No features available.`) change because `llm-provider` is registered; regenerating them is part of this spec.

## 2. Functional Requirements

### Extensions to the add mechanism (spec 004)

- FR-001 (ubiquitous)    The feature contract of spec 004 (its FR-003) shall accept a multi-choice input with these extra rules, checked by the same contract test: only the last input of a feature may be multi-choice; it declares a non-empty list of distinct, non-empty choices and no validator; it may declare its item noun (plural) and, per choice, its item file, which must be a `create` entry of the feature plan for any set of values that includes that choice. The content of a `shared` entry shall not depend on the values of the multi-choice input; the contract test renders each `shared` entry for every non-empty set of values and checks that they are byte-identical.
- FR-002 (event-driven)  WHEN a feature with a multi-choice input is called directly (spec 004 FR-006), the CLI shall accept one or more positional arguments for that input after the other inputs, trimmed as in spec 004, and shall check them in spec 004's order with these changes: "too few arguments" means no value for the multi-choice input (`Error: <feature> requires <input>`); there is no "too many arguments" check for it; each value shall be one of the choices (spec 004 EC-009) and shall not repeat another value, otherwise it fails with `Error: <input> "<value>" is given more than once`, naming the first repeated value. The usage line shows the input as `<input>...` (e.g. `Usage: aicli add llm-provider <provider>... [flags]`).
- FR-003 (event-driven)  WHEN a feature that declares item files is run with values of which one or more are already added (their item file exists, of any kind), the shared mechanism shall create and modify nothing and fail as in spec 004 FR-026 with the heading `cannot add <feature>, these <items> are already added:` and one continuation line `<value> (<item file>)` per added value, in choice order, in place of the message of spec 004 FR-023, whatever other `create` entries exist (e.g. the test file of an added provider). The message of spec 004 FR-023 is used only when none of the values is added and one or more `create` entries exist.
- FR-004 (ubiquitous)    The values of a multi-choice input shall be passed to the feature plan, shown in the equivalent command and reported in choice declaration order, whatever order the user gave them in, so that `aicli add llm-provider ollama openai` and `aicli add llm-provider openai ollama` produce the same plan, the same output and the same equivalent command (`aicli add llm-provider openai ollama`).
- FR-005 (event-driven)  WHEN `aicli add <feature>` is run in interactive mode inside a project root with no positional arguments and no flags, and the feature declares one or more inputs, the CLI shall open the form of that feature directly (spec 004 FR-011), without the selector, in the alternate screen. This supersedes spec 004 FR-006 for this case only. From there the flow is that of spec 004 FR-011..FR-019, except that `Esc` in the form quits as `Ctrl+C` does in spec 004 FR-010, since there is no selector to return to; `Esc` in the confirmation still returns to the form (spec 004 FR-018). A feature that declares no inputs, a call in static mode, and a call with one or more positional arguments or flags behave as in spec 004 FR-006.
- FR-006 (state-driven)  WHILE a multi-choice field has the focus, the form shall show every choice on its own line in declaration order with `[x] ` before each selected choice and `[ ] ` before each unselected one, and a cursor `> ` on exactly one line (starting on the first choice that is not already added; on no line when every choice is already added, EC-006), so that selection and cursor are visible without colour; `↑`/`↓` and `k`/`j` move the cursor, staying put at the ends; `Space` toggles the choice under the cursor; a click on a choice moves the cursor to it and toggles it. Nothing is selected at the start. WHILE it does not have the focus, it shall show the selected choices on one line separated by `, `, or nothing if none is selected. Pressing `Enter` with nothing selected shall show the error `select at least one <input>` as spec 004 FR-013 does; since a multi-choice field is always the last one, leaving it with `Shift+Tab` or a click does not validate it (spec 004 FR-015).
- FR-007 (state-driven)  WHILE the form of a feature that declares item files is shown, every choice whose item file exists shall be drawn as `[✓] <choice> (already added)`, dimmed when styled, and shall not be selectable: the cursor skips it and `Space` and clicks on it do nothing. This check is read-only and happens when the form opens; it is the only file-system access of the form, as an exception to spec 004 FR-020.
- FR-008 (ubiquitous)    The shared mechanism of spec 004 (FR-022..FR-025) shall accept a file action per entry of the feature plan: `create` behaves as in spec 004; `shared` is created like `create` when its path does not exist and is left untouched when it exists as a regular file or as a symbolic link to a regular file inside the project root (any other kind fails, EC-028); `inject` names an existing file, a marker name and one or more lines, rendered from embedded templates like the feature files (ARC-5). Every path, of any action, is validated as in spec 004 FR-022 (including symbolic links resolving inside the project root), and the same path may not appear in two entries, except that several `inject` entries may target the same file (applied in plan order).
- FR-009 (event-driven)  WHEN the shared mechanism applies the `inject` entries of a file, it shall treat each entry as one block of lines that is never split: IF the file, including the blocks inserted by earlier entries of the same run, already contains the entry's lines as consecutive full lines (each compared after removing leading and trailing whitespace), THEN that entry inserts nothing, so that two identical entries insert their block once; otherwise all its lines are inserted, in order, including those that also appear elsewhere in the file (e.g. a blank line, `return`, `)`), so that a later feature can inject a whole method or class. The blocks inserted at the same marker in one run go right after the marker line, one after another in plan order, so that they land above the lines of earlier runs. Each inserted non-empty line is prefixed with the marker's leading whitespace and keeps its own relative indentation; an empty line is inserted empty. Inserted lines use the file's line ending (`\n`, or `\r\n` if the marker line ends with it; EC-030). If no entry inserts anything, the file is not modified. The file is modified in place at the path its symbolic links resolve to, keeping its permissions, so that a symbolic link stays a symbolic link (EC-029). Nothing else in the file shall change, byte for byte. This is the only way an existing file is modified, and it does not overwrite it (SEC-5).
- FR-010 (unwanted)      IF, before anything is written, an `inject` target does not exist (including a broken symbolic link), or exists but, once its symbolic links are resolved, is not a regular file, or has no marker of the given name, or has more than one, THEN the shared mechanism shall create and modify nothing and fail as in spec 004 FR-026 with `Error: cannot add <feature>, <path> does not exist`, `Error: cannot add <feature>, <path> is not a regular file`, `Error: cannot add <feature>, <path> has no "# aicli:<name>" marker` or `Error: cannot add <feature>, <path> has more than one "# aicli:<name>" marker`, for the first such entry in plan order. These checks run after those of spec 004 FR-022 and before those of FR-003 and spec 004 FR-023.
- FR-011 (event-driven)  WHEN the shared mechanism succeeds, it shall report, in plan order and one line per path (a file injected by several entries is reported once, at its first entry): `create  <path>` for each created `create` or `shared` file, `skip    <path>` for each `shared` file that already existed, and `update  <path>` for each file modified by injection (a file where no entry inserts anything is reported as `skip`). Then the success line and next steps of spec 004 FR-025, styled the same way. The confirmation (spec 004 FR-018) shall show `Will create:` with the `create` entries and the `shared` entries that do not exist, and `Will update:` with the files that injection would modify, each heading only when it has paths; shared files that exist and injections that change nothing are not shown. On a terminal too short for them, both headings and their paths scroll together as one list, with the scroll keys and indicator lines of spec 004 EC-010. Before showing it, the confirmation shall run, without writing anything, the checks of spec 004 FR-022, FR-010, FR-003 and spec 004 FR-023 (including the `shared` paths of EC-028), in that order, the same as the run, and show the first failure in place of both lists as spec 004 FR-018 states. All-or-nothing (spec 004 FR-024) shall cover injected files too: on any failure every modified file shall get back its original content, byte for byte, and the rollback error of spec 004 FR-024 lists any file it could not restore.

### The `llm-provider` feature

- FR-012 (ubiquitous)    The CLI shall provide the feature `aicli add llm-provider` (short description `Add one or more LLM providers.`) with one multi-choice input `provider` (description `LLM providers to add`) whose choices are `openai`, `claude`, `gemini`, `ollama`, item noun `providers` and item file `app/ai/llm/<provider>.py`, so that it can be run as `aicli add llm-provider <provider>...`, from the selector of `aicli add`, or as `aicli add llm-provider` in a terminal (FR-005).
- FR-013 (event-driven)  WHEN `aicli add llm-provider` runs with a valid set of providers, its feature plan shall be, in this order: the `shared` files `app/ai/llm/__init__.py`, `app/ai/llm/base.py`, `app/services/llm.py`, `app/schemas/llm.py`, `app/api/routers/llm.py`, `tests/test_llm_router.py`; then, per provider in choice order, the `create` files `app/ai/llm/<provider>.py` and `tests/test_llm_<provider>.py`; then the `inject` entries: `app/api/router.py` at `# aicli:router-imports` (the import of the `llm` router) and at `# aicli:routers` (its `include_router` line), `pyproject.toml` at `# aicli:dependencies`, one entry per SDK (the SDK of each provider: `openai` for `openai` and `ollama`, `anthropic` for `claude`, `google-genai` for `gemini`, each SDK once), and `.env.example` at `# aicli:env`, one entry per line (the required variables of each provider in the order of the definition of configured provider, each as `NAME=` with an empty value, never a real value; for `ollama`, followed by its optional variable as the comment `# OLLAMA_BASE_URL=http://localhost:11434/v1`), so that a line already present skips only its own entry (FR-009).
- FR-014 (event-driven)  WHEN the files are created, the feature shall declare these next steps, in order: `Run uv sync to install the provider SDKs`, then, per provider in choice order, `Set <VAR>, <VAR> in .env` with the required variables of that provider (definition of configured provider).
- FR-015 (ubiquitous)    The base skeleton of spec 001 shall contain the markers this feature needs: `# aicli:dependencies` inside the `dependencies` array of `pyproject.toml`, `# aicli:env` at the end of `.env.example`, and, in `app/api/router.py`, `# aicli:router-imports` where router imports go and `# aicli:routers` where routers are included, so that a project generated by `aicli new` accepts `aicli add llm-provider` with no manual change; the generated project shall still pass its own pytest and ruff (TST-3, TST-5). Every block injected into a Python file, by this or any later feature, at any marker and in any order (here `# aicli:router-imports` and `# aicli:routers`; later, the markers of FR-022), shall pass `ruff check` and be left unchanged by `ruff check --fix` and `ruff format`, so that FR-009 still finds it as consecutive full lines on a later run and never inserts it twice.

### The generated project

- FR-016 (ubiquitous)    The generated `app/ai/llm/` package shall expose, without importing any provider SDK at module load: one async protocol per capability, of which this spec defines only `CompletionClient`, with one method that takes a list of messages, an optional system prompt and a maximum number of tokens, and returns the generated text; the message type (role `user` or `assistant`, text content); and a registry that finds the added providers at runtime, from the modules of the package that declare themselves as provider modules (each provider module declares its provider name, its position in the declaration order of the choices and its required variables), never from a list written into a shared file, so that a provider module written by the user is found too (definition of added provider); any other module of the package (`base`, a helper written by the user) is ignored. The registry returns, for each added provider, its name, whether it is configured, the names of its missing variables and whether its client implements a given capability, and builds its client. Each provider SDK shall be imported only when a client of that provider is built or used, so that the project's tests pass before `uv sync` installs the SDKs.
- FR-017 (ubiquitous)    Each `app/ai/llm/<provider>.py` shall read its settings from the environment and the root `.env` through pydantic-settings with the prefix of the provider (definition of provider), with the variables of the definition of configured provider and no model default, and implement `CompletionClient` asynchronously with the provider's SDK (`claude` with `anthropic`, `gemini` with `google-genai`, `ollama` through the `openai` SDK at `OLLAMA_BASE_URL`, with no API key required). An optional variable that is unset, empty or whitespace only takes its default. Each client shall never let the SDK take a credential or an endpoint from the environment (e.g. `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `ANTHROPIC_BASE_URL`, `GOOGLE_API_KEY`): it passes its key, model and base URL to the SDK explicitly from its own settings, the base URL being the vendor's default when the provider has no variable for it; other environment the SDK or its HTTP client reads (e.g. proxy variables) is not affected. `ollama` passes a fixed placeholder key, so that it never sends another provider's key to `OLLAMA_BASE_URL` (SEC-1, ERR-4).
- FR-018 (event-driven)  WHEN the generated app receives `GET /llm/health`, it shall answer `200` with a body that holds `status` (`ok` if every added provider is configured, including when there is none, `degraded` otherwise) and `providers`: one entry per added provider (empty when there is none), in the order of their declared positions (for the four providers of this spec, the declaration order of the choices), with `name`, `configured` (boolean) and `missing` (the names of its required variables that are unset, empty or whitespace only, in the order it declares them, which for the four providers of this spec is the order of the definition of configured provider; empty when configured). It shall make no network call and never include the value of any variable.
- FR-019 (event-driven)  WHEN the generated app receives `POST /llm/{provider}/completion` for a configured added provider with a valid body (`messages`: a non-empty list of messages; `system`: optional string; `max_tokens`: optional integer from 1 to 32768, default 1024), the router shall only translate HTTP and call the completion use case of `app/services/llm.py`, which gets the client from the registry and calls it; the app shall answer `200` with `provider`, `model` (the configured model) and `content` (the generated text).
- FR-020 (unwanted)      IF the `{provider}` of `POST /llm/{provider}/completion` is not an added provider (a name that no provider module found by the registry declares), THEN the app shall answer `404`; IF it is added but not configured, THEN `503`; IF it is configured but its client does not implement the capability of the route (here `completion`), THEN `501`; IF the body is invalid, THEN `422`; IF the provider call fails for any reason (authentication, rate limit, timeout, network, unexpected response), THEN `502`. Every error body shall be the `ErrorModel` of the skeleton with its fixed message (`Bad Gateway`, `Service Unavailable`, `Not Implemented`, etc.), and the app shall log only the exception type name, never the API key, the request messages or the provider's response body (ERR-4, SEC-1). When several of these apply, the first in this order wins: `404`, `422`, `503`, `501`, `502`. `{provider}` is matched as free text, so that any name reaches the registry, and a name it does not find gets `404` instead of failing validation.
- FR-021 (ubiquitous)    The generated tests shall cover FR-016..FR-020 and FR-022 using fake clients (one implementing `CompletionClient`, one not, for the `501`) and environment overrides, and shall make no network call and need no provider SDK installed (TST-6). Where a test needs a provider SDK (e.g. to check what a client passes to it, EC-026) or its absence (EC-018), it shall replace the SDK module with a fake or a missing one for that test, so that the same tests run and pass in both states below, none of them skipped. The generated tests shall not depend on the developer's environment: they run with every provider variable unset and without reading the project's `.env`, except for the values each test sets itself. After `aicli add llm-provider` with any set of providers, and again after adding more providers in a later run, the generated project shall pass its own pytest and `ruff check` in two states: without the provider SDKs, in the environment synced with `uv sync` before that run of `aicli add` and running both without syncing again (e.g. `uv run --no-sync`), so that the dev tools are installed and the SDKs added by that run are not; and with them, after `uv sync`.
- FR-022 (ubiquitous)    So that later features can add a capability to all or only some providers with the injection of FR-009, each layer in its own existing file, the generated files shall contain these markers, each exactly once: `# aicli:capabilities` in `app/ai/llm/base.py` (where capability protocols go), `# aicli:methods` in each `app/ai/llm/<provider>.py` (where that provider's capability methods go, inside its client class), `# aicli:schemas` in `app/schemas/llm.py` (where request and response models go), `# aicli:services` in `app/services/llm.py` (where use cases go) and `# aicli:routes` in `app/api/routers/llm.py` (where capability routes go, which only translate HTTP as in FR-019). A generated project with only the markers and no injected lines shall pass its own pytest and ruff.

## 3. Edge Cases

- EC-001 IF `aicli add llm-provider` is called directly with no provider in static mode (no TTY), THEN it shall fail as in FR-002 with `Error: llm-provider requires provider` and the usage line, and create nothing. (FR-002, FR-005)
- EC-002 IF a provider is given twice (e.g. `openai openai`, or ` openai` and `openai` after trimming), THEN the call shall fail with `Error: provider "openai" is given more than once` and create nothing. (FR-002)
- EC-003 IF a value differs from a provider only in case (e.g. `OpenAI`) or is a name outside the choices, including the vendor or product name of a provider (e.g. `anthropic`, `chatgpt`), THEN the call shall fail as in spec 004 EC-009, listing `openai, claude, gemini, ollama`. (FR-002, FR-012)
- EC-004 IF some of the requested providers are added and others are not (e.g. `openai` added, `openai claude` requested), THEN nothing shall be created or modified and the error shall list only the added ones (`  openai (app/ai/llm/openai.py)`), even though `tests/test_llm_openai.py` exists too. (FR-003)
- EC-005 IF an item file exists as a directory or a broken symbolic link, THEN that provider counts as added in the form (FR-007) and in the error (FR-003). (FR-003, FR-007)
- EC-006 IF every provider is already added and the form is opened, THEN the multi-choice field shall show all of them as `(already added)`, show `All providers are already added.` in place of the field error and no cursor on any line, and `Enter` shall do nothing and not be listed in the footer; only `Esc` and `Ctrl+C` leave. (FR-006, FR-007)
- EC-007 IF a provider's item file is added by another process after the form opened, THEN the confirmation or the run shall fail as in FR-003, never replacing it (spec 004 EC-018). (FR-003, FR-007)
- EC-008 IF `ollama` is added when `openai` is already added, or both are requested together, THEN the `openai` SDK shall appear once in `pyproject.toml` (FR-009 skips the entry already present) and the report shall show `skip` or `update` for `pyproject.toml` accordingly. (FR-009, FR-011, FR-013)
- EC-009 IF a `shared` file was deleted by the user after a previous run (e.g. `app/api/routers/llm.py`), THEN a later run shall create it again (`create`); IF it exists but was edited by the user, THEN it shall be left untouched (`skip`). (FR-008, FR-011)
- EC-010 IF the project was generated before this spec, so `pyproject.toml`, `.env.example` or `app/api/router.py` has no marker, or the user removed or duplicated one, THEN the run shall fail as in FR-010 naming the first such file and marker, and the confirmation shall show that error in place of the file lists, with only `Cancel` (spec 004 FR-018). (FR-010, FR-015)
- EC-011 IF the line to inject is already in the file because the user added it by hand (e.g. `"openai>=…"` in `dependencies`, or `OPENAI_API_KEY=` in `.env.example`), THEN that entry shall not be inserted again, while the other entries of the run still are; the comparison is by full line after removing leading and trailing whitespace, so a line with a different version bound counts as a different line. (FR-009)
- EC-012 IF an injection target uses `\r\n` line endings, or its marker is indented (e.g. inside the TOML array), THEN the inserted lines shall use the same line ending and indentation, and the file shall stay valid TOML / Python. (FR-009, FR-015)
- EC-013 IF writing an injected file fails, or any later step of the run fails, THEN every file already injected in that run shall be restored byte for byte and every created file removed (spec 004 FR-024); a signal during the run completes that rollback first (spec 004 EC-023). (FR-011)
- EC-014 IF an injection target is a symbolic link that resolves outside the project root, THEN the run shall fail as in spec 004 FR-022 and modify nothing. (FR-008)
- EC-015 IF, in the multi-choice field, the user presses `Space` on the cursor line that is already selected, THEN it shall be deselected; IF the terminal is too short for all choices, THEN they scroll inside the field keeping the cursor visible (spec 004 EC-010). (FR-006)
- EC-016 IF `Esc` is pressed in the form opened by `aicli add llm-provider` (FR-005), THEN the CLI shall restore the terminal, print nothing, create nothing and exit with 0; IF the same form was opened from the selector of `aicli add`, THEN `Esc` returns to the selector (spec 004 FR-017). (FR-005)
- EC-017 IF, in the generated app, a provider's variable is set to whitespace only, THEN it shall count as missing in `/llm/health` and `POST /llm/{provider}/completion` shall answer `503`. (FR-018, FR-020)
- EC-018 IF the provider SDK is not installed (no `uv sync` yet) and `POST /llm/{provider}/completion` is called for a configured provider, THEN the app shall answer `502` and log only the exception type, and `GET /llm/health` shall keep working. (FR-016, FR-020)
- EC-019 IF `messages` is empty, holds a role other than `user` or `assistant`, or `max_tokens` is outside 1..32768, THEN the app shall answer `422`. (FR-019, FR-020)
- EC-020 IF `app/ai/llm/__init__.py` was deleted by the user and a later run creates it again, THEN `GET /llm/health` shall list every added provider, including those added by earlier runs. (FR-001, FR-016, FR-018)
- EC-021 IF the user runs `ruff check --fix` and `ruff format` on the project between two runs of `aicli add llm-provider`, THEN the later run shall not inject any line again and the project shall still pass `ruff check`. (FR-009, FR-015)
- EC-022 IF `POST /llm/{provider}/completion` has an invalid body and a `{provider}` that is not added, THEN the app shall answer `404`; IF the provider is added but not configured and the body is invalid, THEN `422`. (FR-020)
- EC-023 IF `OLLAMA_BASE_URL` is set to an empty or whitespace-only value (e.g. `.env.example` copied to `.env` and the comment removed without a value), THEN the `ollama` client shall use `http://localhost:11434/v1`, and `ollama` shall still count as configured when `OLLAMA_MODEL` is set. (FR-017, FR-018)
- EC-024 IF the developer has a `.env` with real provider values, or exports provider variables in the shell, THEN the generated tests shall pass as if neither existed and still make no network call (TST-6). (FR-017, FR-021)
- EC-025 IF an `inject` entry has several lines and some of them also appear elsewhere in the target (e.g. a blank line or `return`), THEN the whole block shall be inserted; IF the block already appears in the target as consecutive lines, THEN it shall not be inserted again. (FR-009)
- EC-026 IF `OPENAI_API_KEY` or `GOOGLE_API_KEY` is set in the generated app's environment, THEN the `ollama` client shall not send it to `OLLAMA_BASE_URL` and the `gemini` client shall use `GEMINI_API_KEY`; IF `OPENAI_API_KEY` is unset, THEN the `ollama` client shall still be built. (FR-017)
- EC-027 IF `app/ai/llm/` holds a module that does not declare itself as a provider module (e.g. a `utils.py` written by the user), THEN the registry shall ignore it and `/llm/health` shall not list it; IF it holds a provider module written by the user whose name is not one of the choices of this spec (e.g. `mistral`), THEN the registry shall find it: `/llm/health` shall list it at its declared position with its declared variables, and `POST /llm/mistral/completion` shall follow FR-019 and FR-020 like any added provider; aicli neither generates nor validates such a module. (FR-016, FR-018, FR-020)
- EC-028 IF the path of a `shared` entry exists but is not a regular file nor a symbolic link to a regular file inside the project root (e.g. a directory or a broken symbolic link), THEN the run shall fail as in spec 004 FR-023, listing that path in plan order among any existing `create` paths, and create and modify nothing. (FR-008)
- EC-029 IF an `inject` target is a symbolic link that resolves inside the project root, THEN the file it resolves to shall be modified, the link shall stay a link, and the file shall keep its permissions, also after a rollback. (FR-009, FR-011)
- EC-030 IF a marker is the last line of its file and has no line ending, THEN the mechanism shall add after it the line ending of the first line of the file that has one (`\n` if none has) and end every inserted line with it, so that the marker and each inserted line stay on lines of their own. (FR-009)
- EC-031 IF two modules of `app/ai/llm/` declare the same provider name (e.g. a copy `openai_old.py` of `openai.py`), THEN the registry shall use only the module that is that provider's item file (`<name>.py`) and ignore the other; IF neither is, THEN the registry shall ignore both; IF two providers declare the same position, THEN they shall be listed in the alphabetical order of their names. (FR-016, FR-018)

## 4. Scope

### In scope
- Multi-choice inputs, direct form on a terminal, item files and the "already added" error, as generic extensions of the add mechanism of spec 004.
- `shared` and `inject` file actions with markers, confirmation and report, all-or-nothing including injected files.
- Markers in the base skeleton (`pyproject.toml`, `.env.example`, `app/api/router.py`).
- The `llm-provider` feature with `openai`, `claude`, `gemini` and `ollama`: async clients, settings per provider, registry, `llm` service and router with `/llm/health` and `/llm/{provider}/completion`, schemas and tests.

### Out of scope
- Calling the real provider from `/llm/health`: it would need network and cost money on every check (TST-6).
- YAML configuration or per-provider env files: one `.env` with prefixed variables covers flat settings with no new dependency (STK-4).
- Running `uv sync` from the CLI: it needs network and cannot be rolled back; it is a next step.
- Model defaults: model names go stale, so the model is a required variable.
- Removing or updating providers: there is no registry of added features (spec 004); a later spec can add `remove`.
- Other providers (e.g. Mistral, Cohere): each needs its own dependency approval; the choice list grows in a later spec. A user may write such a provider module by hand and the registry finds it (EC-027), but aicli does not generate, validate or test it: its behaviour, including in `/llm/health`, is the user's responsibility.
- Capabilities beyond completion (streaming, embeddings, tools, structured output), for all or some providers: later features add them at the markers of FR-022.
- Provider-specific code generated by aicli (e.g. OpenAI image generation outside a capability): aicli only generates capabilities through the common protocols; anything else is the user's own code.
- Injecting into files without a marker (heuristic anchors): fragile and hard to specify; projects without markers get a clear error.
- A constitution rule that every generated router exposes its own `/health`: pending approval through `sdd-constitution`; this spec already follows it.
- Windows support: LIM-1.
